Git作为强大的工具，是每个程序员必不可少的。在具体讲解Git的用法之前，我们先来说说什么是Git。
# 版本控制 
>**版本控制 Version Control System VCS**是一种*记录一个或若干文件内容变化，以便将来查阅特定版本修订情况的系统*。
{: .prompt-info }

当我们开发项目时，难免会需要记录同一个文件的不同版本：比如，单纯的备份；又或者，你突发奇想希望尝试一个新的想法……在没有版本控制的时代，你只能拷贝一份文件，在这份文件上做修改，并重命名以作区分：
```txt
看片神器初代 20xx-1-1
看片神器二代 20xx-2-2
看片神器β 20xx-3-3
看片神器三代 20xx-4-4
```
这样的方式确实简单易懂，但一旦混淆就会犯错；每个文件都有大部分的重复；最重要的是，你不能轻松比较文件之间的差异，不能直接合并文件的差异，对各个版本的关系也不甚明了。
## 本地版本控制系统
为了解决这个问题，人们发明**本地版本控制系统**，其中的代表作是**RCS**。它只存储文件的最新版本和*旧版本与新版本的差异补丁*（比如，A比B少了什么、多了什么），这能极大节省磁盘空间。

当然，这也意味着你的磁盘一坏，所有文件都会消失；而且作为远古时代的产物，它只能管理单个文件，也无法实现和别人共享你的项目。
## 集中化版本控制系统
为了让多为开发者能够携手共进，**集中化版本控制系统 Centralized Version Control Systems CVCS**应运而生。在这种系统中，会有一个进行集中管理的服务器，保存所有文件的修订；而人们可以通过客户端取出最新文件或提交更新。

这种方式的缺陷就在于，中央服务器会成为协同开发的刚需：假如断网一小时，谁也无法提交更新；服务器的磁盘一损坏，就只剩下每个人零散的本地文件。
## 分布式版本控制系统
时至今日，人们主要使用的是**分布式版本控制系统 Distributed Version Control System DVCS**，我们要说的Git就是其中一员。

在这种系统中，用户的本地都会*有完整的镜像仓库*；用户的每次获取更新，都是一次完整的备份，这样就算服务器坏了，也能直接换新的。这种系统都可以指定和若干不同的远端代码仓库交互，因此在同一个项目，你能和不同分工的小组相互协作。
# Git的独特之处
那么，既然分布式版本控制系统不止一种，为什么Git能做到出类拔萃？
由于暂不清楚Git的底层实现，这里我们只解释存储方式上的优势。
### 存储方式
#### 基于差异
就像之前所讲，*只记录变化*是一种容易想到的节约空间的记录方式，这种方式被称为**基于差异 delta-based**的版本控制。

对于项目的每个文件，首先保存第 1 个完整文件，然后保存第 2 个版本相对于第 1 个版本改动了哪几行，再保存第 3 个版本相对于第 2 个版本的差异……以此类推。

不过这样以来，如果你想看第 100 个版本的完整内容，系统必须从第 1 个版本开始，把 1 到 100 的所有差异逐条“打补丁”应用一遍，才能算出最终结果。这个过程在版本数量多时非常慢，且一旦中间的某个补丁丢失，后续全废。
#### 记录快照
而Git则有不同的思路。对于记录方式，它采取了非常朴实的方式：既然记录变化算得麻烦，那干脆记录所有版本吧！具体来说，你*每一次提交*，它都会对*所有文件*创建一个*快照*。这样你就能实现在众多版本中*全场游龙*！

那么你可能就要想了：“欸~把所有版本都拷贝一遍，很浪费磁盘~~的说~~！”。

非也非也，Git不是直接复制粘贴：
- 对于没变的文件，它只会存储一个*指针*（即链接），即在实现上，并不重复存储未修改的内容。
- 对于修改后文件的快照，会将它们*压缩*存储，节省空间。
- 对于一大堆相似的远古快照，Git会偷偷地进行之前所说的 *“转换为差异”* 的打包操作：选相对新的文件作为基座，旧版本就转化为差异补丁。这些打包后的文件会一直沉睡，直到你去唤醒它们。
